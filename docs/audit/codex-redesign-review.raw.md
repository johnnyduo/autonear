## Pass 1: plan review

## Plan review — ranked findings

1. **Critical — owner sessions can cross vault boundaries.** The plan authorizes an address that owns *any* attached vault, then lets that session approve or reject *any* decision and change deployment-wide mode, Watch settings, and pause state. There is no decision-to-vault or chain scope. A configured `OWNER_ADDRESS` is also treated as an alternative to the current on-chain owner, with no stated precedence or stale-owner handling. Define one authoritative owner for this single-owner deployment and bind every owner action to that scope before applying `needOwner`. [Plan:37–41](docs/superpowers/plans/2026-11-06-owner-app-redesign.md), [app.js:203](/Library/WebServer/Documents/autonear/src/app.js:203), [vault/index.js:335](/Library/WebServer/Documents/autonear/src/vault/index.js:335).

2. **High — challenge replay protection is underspecified.** “Delete nonce on use” is not an atomic consume: concurrent session requests can both pass a read-then-delete check, especially on D1, whose `tx()` is explicitly non-atomic. Bind the signed challenge to domain, origin, chain, address, issued time and expiry; consume the nonce with a single conditional write and check the affected row count. Test concurrent redemption on both database backends. [Plan:36–41](docs/superpowers/plans/2026-11-06-owner-app-redesign.md), [db.js:157](/Library/WebServer/Documents/autonear/src/db.js:157).

3. **High — Manual and top-up do not fit the current loop placement.** `processVault` currently returns before reading chain state when there are no pending deploy candidates. A top-up placed “before candidates” needs to move the chain gates ahead of that return. Manual must still allow `reconcile` to complete, but mode must be rechecked immediately before each claim, draw, and deploy; the existing `stillOk` checks only loop state and kill switch. [Plan:25,48–52](docs/superpowers/plans/2026-11-06-owner-app-redesign.md), [autonomy.js:115](/Library/WebServer/Documents/autonear/src/autonomy.js:115), [autonomy.js:118](/Library/WebServer/Documents/autonear/src/autonomy.js:118), [autonomy.js:261](/Library/WebServer/Documents/autonear/src/autonomy.js:261).

4. **High — rule (j) weakens the existing gas invariant without a recovery design.** Rule (g) currently draws the minimum needed for one verified deployment. A standalone top-up can spend mandate budget with no deploy and can repeat after a crash or pending transaction because a ten-minute timestamp is neither a durable claim nor a chain outcome. The plan also omits draw-fee estimation, the agent’s seed gas requirement, pending-receipt reconciliation, and an atomic per-vault claim. Reuse the existing parity check against a fresh pinned state, then ledger and reconcile the submitted transaction before another top-up. [Plan:48–52](docs/superpowers/plans/2026-11-06-owner-app-redesign.md), [autonomy.js:14](/Library/WebServer/Documents/autonear/src/autonomy.js:14), [autonomy.js:188](/Library/WebServer/Documents/autonear/src/autonomy.js:188), [autonomy.js:239](/Library/WebServer/Documents/autonear/src/autonomy.js:239).

5. **High — owner approval can bind an arbitrary signer.** `approveDecision` requires `nonce`, `payloadHash`, confirmation phrase, and `signer`; for deploys it validates the signer’s *format*, not that it equals the session wallet. The new Approvals card describes a simple hold action but does not specify how those fields are supplied or prevent a wallet owner from approving a deploy for another signer. Bind owner-session approvals to the authenticated address where appropriate, and retain an explicit review of the exact payload and signer. [Plan:90–92](docs/superpowers/plans/2026-11-06-owner-app-redesign.md), [app.js:203](/Library/WebServer/Documents/autonear/src/app.js:203), [decisions.js:40](/Library/WebServer/Documents/autonear/src/decisions.js:40).

6. **Medium — Watch can bypass signal and prompt-safety gates.** A keyword boost must never turn an item without NEAR evidence into `isNear`, and it must not lift injection-flagged content into model prompts. Excludes need defined matching boundaries to avoid suppressing unrelated findings; source IDs must be restricted to registered connectors. Apply owner settings in the common ingestion path, including direct `ingestSource` calls, and preserve `forceTags` treatment deliberately. [Plan:59–60](docs/superpowers/plans/2026-11-06-owner-app-redesign.md), [relevance.js:73](/Library/WebServer/Documents/autonear/src/relevance.js:73), [relevance.js:76](/Library/WebServer/Documents/autonear/src/relevance.js:76), [ingest.js:22](/Library/WebServer/Documents/autonear/src/ingest.js:22), [ingest.js:49](/Library/WebServer/Documents/autonear/src/ingest.js:49).

7. **Medium — the five-second product path is still incomplete.** “Connect wallet” as the only landing action blocks visitors without an injected EVM wallet from seeing the four-page experience; the proposed demo fallback should be directly explorable. The Home sentence must distinguish *watching*, *able to act*, and *acting now*: a hosted Worker can ingest but cannot sign. Show a concrete example of a real vault transaction and its owner-set limit near the primary promise; a decorative scene plus counts does not prove the contract-backed claim. [Spec: landing and demo decisions](docs/superpowers/specs/2026-11-06-owner-app-redesign-design.md), [wallet/config.js:3](/Library/WebServer/Documents/autonear/web/src/wallet/config.js:3), [worker.js:45](/Library/WebServer/Documents/autonear/src/worker.js:45).

8. **Medium — several tasks claim flows the current code does not provide.** “Update limits” cannot work through the owner session because `/api/vault/mandates/propose` remains operator-only; owner withdraw and on-chain emergency pause have no planned transaction builder, only grant-plan transactions and a grant-specific `TxSender`. The plan should add concrete owner transaction generation, verification, and UI tasks, or narrow those promises. `#/activity` is also specified as a drawer route without a return-route rule. [Plan:16,67,100–108](docs/superpowers/plans/2026-11-06-owner-app-redesign.md), [app.js:248](/Library/WebServer/Documents/autonear/src/app.js:248), [TxSender.jsx:25](/Library/WebServer/Documents/autonear/web/src/wallet/TxSender.jsx:25).

9. **Medium — portability and test coverage need explicit tasks.** `node:crypto` in shared request code needs a Workers build check; the proposed test list omits concurrent nonce use, account or chain switching after sign-in, owner transfer, mode change between claim and send, and pending top-up recovery. EOA-only signing also excludes contract-wallet and multisig owners even though the current vault UI recommends multisig; label that limitation in the sign-in flow and define the operator path for those owners. [Plan:34–42,48–52](docs/superpowers/plans/2026-11-06-owner-app-redesign.md), [worker.js:1](/Library/WebServer/Documents/autonear/src/worker.js:1), [Propose.jsx:105](/Library/WebServer/Documents/autonear/web/src/views/vault/Propose.jsx:105).

**Recommendation:** resolve findings 1–4 in the plan before implementation. They determine the authorization boundary and whether rule (j) preserves the loop’s current safety guarantees.

## Pass 2: implementation review

## Ranked findings

1. **High — Top-up can repeat while the first transaction’s outcome is unknown.** [src/autonomy.js](/Library/WebServer/Documents/autonear/src/autonomy.js:366) replaces a stale `submitted` claim after 30 minutes without reconciling its transaction receipt. If a draw was broadcast but its hash was not saved, or its receipt is delayed, the next tick can send another draw against the same low balance. Keep submitted claims until the chain outcome is established; treat a missing hash after a send as an unknown outcome requiring operator resolution.

2. **High — “Emergency stop” leaves the vault active on chain.** [VaultPage.jsx](/Library/WebServer/Documents/autonear/web/src/app/VaultPage.jsx:26) only pauses server controls. The separate on-chain pause button is optional, so the success message “The agent is stopped” can appear while an agent key can still call the vault directly. Make the stop flow include the owner’s `pause()` transaction and report partial completion explicitly.

3. **High — Manual mode does not prepare requests as the UI promises.** [src/autonomy.js](/Library/WebServer/Documents/autonear/src/autonomy.js:125) returns after reconciliation; it creates no approval. [Approvals.jsx](/Library/WebServer/Documents/autonear/web/src/app/Approvals.jsx:53) says the agent “asks you before it does anything.” A user switching to Manual may wait for requests that never appear. Implement request creation or change the copy to describe the actual behavior.

4. **Medium — Session domain binding trusts the request Host header.** [src/app.js](/Library/WebServer/Documents/autonear/src/app.js:157) uses `url.host`, which the Node adapter builds from the client supplied Host header in [src/server.js](/Library/WebServer/Documents/autonear/src/server.js:34). A request through a permissive proxy can obtain and redeem a challenge labelled with an attacker chosen domain. Bind challenges to a configured public origin or validated host allowlist.

5. **Medium — A valid owner session can record receipts and obtain deploy bytecode beyond its stated scope.** [src/app.js](/Library/WebServer/Documents/autonear/src/app.js:273) and [src/app.js](/Library/WebServer/Documents/autonear/src/app.js:278) use `needOwner`; the plan specifies both routes as operator only. A stolen browser session can submit receipt verification requests and retrieve full approved deploy data. Restore `needOperator` on those routes.

6. **Medium — A pending top-up is ledgered as confirmed.** [src/autonomy.js](/Library/WebServer/Documents/autonear/src/autonomy.js:376) records `status: 'confirmed'` when `res.status === 'pending'`. Activity and the daily draw count then treat an unconfirmed transfer as completed. Record `submitted`, reconcile the receipt, and mark confirmed only after chain confirmation.

7. **Medium — Wallet account changes can leave the UI showing owner access for the wrong wallet.** [session.js](/Library/WebServer/Documents/autonear/web/src/app/session.js:42) reuses an existing wagmi connection regardless of the selected connector, and its stored `isOwner` state is not refreshed on account changes or against `/api/auth/me`. A user can see enabled owner controls after switching accounts; subsequent on-chain actions use the new account and fail. Subscribe to wallet changes, invalidate the session, and recheck server ownership before enabling controls.
